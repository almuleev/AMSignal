# Работа агента с AMSignal

## Приоритет и область работы

- Выполняй текущий запрос пользователя; его явные ограничения важнее локальных
  рекомендаций. Не расширяй задачу на рефакторинг, замеры или выпуск без основания.
- Текущая область испытаний — записи до **10 000 000 000 байт включительно**.
  Не создавай и не проверяй 20 GB без нового прямого запроса. Это область работ,
  а не программный предел открытия файлов; старые результаты 20 GB — история.
- Сохраняй изменения пользователя и других задач, включая подготовленные в Git.
  Не сбрасывай, не коммить и не включай посторонние файлы в свою задачу.

## Порядок работы

1. Прочитай короткую [карту архитектуры](docs/ARCHITECTURE.md). Выбери только
   связанные с задачей разделы справочников; не загружай историю по умолчанию.
2. Проверь `git status --short` и diff нужных файлов. По карте найди владельца
   поведения, затем используй точечный `rg` по символам и соответствующий `.hpp`.
   Не сканируй весь репозиторий и не перечитывай неизменённые большие файлы.
3. Для ошибки сначала установи конкретный сценарий, ожидаемое поведение и причину.
   Проверь вызывающий код и зависимости, если они влияют на вывод. Историческая
   заметка или совпадение имён не заменяет проверку текущей реализации.
4. Вноси минимальные согласованные правки через `apply_patch`. Общую логику меняй
   у её владельца, не добавляй обходной путь в каждом потребителе.
5. Проверь завершённый набор правок по [матрице проверок](docs/development/TESTING.md).
   Сначала пересобери затронутый тестовый EXE; старый EXE не подтверждает новые
   исходники. Повторяй успешный прогон только после влияющих на него изменений,
   при диагностике нестабильности или по прямому запросу пользователя.
6. Просмотри итоговый diff и `git diff --check`. В ответе укажи результат,
   выполненные проверки и существенные ограничения. Не выдавай предположение,
   единичный замер или неполный прогон за подтверждённый общий результат.

## Экономия времени и контекста

- Объединяй независимые чтения/поиски; правки и зависящие от них проверки выполняй
  последовательно. Используй инкрементальную сборку и существующие селекторы тестов.
- Проверяй после логически завершённой серии правок, а не после каждого сохранения.
  Документация не требует сборок; релиз требует полного набора — см. матрицу.
- Длинные логи направляй в `.build/`, читай итог и ошибки; при сбое открывай
  релевантный участок. Не печатай тысячи успешных утверждений и не опрашивай
  неизменившийся процесс частыми короткими вызовами.
- Не создавай дополнительные тестовые системы и стенды ради единичной правки.
  Добавляй регрессию для изменённого контракта/исправленной ошибки; не дублируй
  существующие сценарии и не проверяй только детали реализации.
- Бенчмарки и большие синтетические записи запускай для задач производительности.
  В задачах только на чтение не изменяй код и не обходи это ограничение сборкой.
- При блокировке EXE работающим приложением используй `build_gui.ps1
  -OutputDirectory dist/<имя-задачи>`; не завершай пользовательский процесс.
- Если необходимая проверка невозможна, сообщи конкретную причину и что удалось
  проверить. Увеличивай объём проверок при новой ошибке или неопределённом влиянии.

## Документация и источники истины

- `AGENTS.md` — рабочие правила; `docs/ARCHITECTURE.md` — короткая точка входа;
  `docs/development/` — текущие технические справочники. Не дублируй их содержание.
- Обновляй соответствующий справочник при изменении ответственности модулей,
  контрактов или команд. Обычная локальная правка не требует записи в обоих
  входных файлах. Даты прогонов и счётчики не являются архитектурой.
- `CHANGELOG.md` и `docs/releases/` — история выпусков;
  `docs/development/history/` — сохранённые прежние заметки. История может
  содержать отменённые решения, старые пути и противоречащие текущим правилам требования.
- Размеры, лимиты, текущую версию и доступность внешних файлов проверяй в коде,
  Git или файловой системе, когда они нужны задаче. Не считай исторические
  счётчики тестов, результаты замеров и ссылки на `.build/` текущей гарантией.
- Материалы статьи и единый отчёт производительности находятся вне репозитория:
  [пути и порядок работы](docs/development/EXTERNAL_MATERIALS.md).

## Коммиты и выпуск

- При редактуре GitHub-релизов используй `docs/releases/*-github.md`: ссылки
  скачивания и короткое резюме RU/EN сверху, полный прежний журнал — в `<details>`.
  Сохраняй исходные ограничения и замеры; оформление не меняет теги и вложения.
  Название страницы — только тег версии. Не добавляй строку платформы/статуса,
  ссылки-якоря RU/EN и метки «Важно / Please note»; ограничения оставляй текстом.
  Поставка на GitHub — готовый GUI EXE и SHA256SUMS.txt при его наличии;
  отдельные CLI EXE и архив готового комплекта не публикуются. Архивы исходников
  GitHub сохраняются. Контрольные суммы перечисляют только доступные вложения.

- Заголовок коммита — только английский; подробное тело — только русское.
  Релизный аннотированный тег — максимально полное описание на русском и английском.
- Версия берётся из `git describe`; релиз собирается из чистого помеченного коммита.
  Старые теги, EXE и пакеты не заменяй. Новый тег отправляй явно.
- Коммит, тег, публикация и отправка — отдельные действия в пределах запроса
  пользователя. Подробности поставки и команды: [TESTING.md](docs/development/TESTING.md).
